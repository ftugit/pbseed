# Публичные профили и чтения из гейтвея — план

Статус: **план** (код не писался). Решение о реализации принимается отдельно.
Дата: 2026-09-18. Связано с: роли пользователей, реестр схемы, курсорная
пагинация, защита гейтвея, конфиг в базе.

## Цель

1. Чтения (GET) из гейтвея для всех таблиц, у которых их нет.
2. Разделение видимых полей по ролям: юзер / модератор / админ
   (часть данных — и гостям).
3. Публичный профиль пользователя (для рендера страницы юзера, в том
   числе гостями).
4. Персональные данные держать отдельно от публичных (задел на
   физическое разделение хранилищ).

## Исходное положение

- `users` уже читается по ролям штатным API (правила реестра: своё +
  весь список админу/модератору). Но почта юзера = открытый ключ,
  «человеческих» полей профиля нет, и гостям не отдаётся ничего.
- Служебные коллекции (`seed_*`) закрыты от штатного API; гейтвей
  отдаёт только свои сессии (`/api/seed/sessions`), политики
  (`/api/seed/policy`) и конфиг (`/api/seed/gateway-config`).
- Чтения журнала и конфига уже разведены по правам (суперюзер/роль
  `admin`).

## Шаг 1 — коллекция `user_profiles` (1:1 к `users`)

Отдельная коллекция в реестре схемы:

| Поле | Тип | Назначение |
|---|---|---|
| `user` | связь → `users`, уникальная | владелец |
| `display_name` | текст ≤64 | отображаемое имя |
| `bio` | текст ≤500 | «о себе» |
| `avatar` | файловое поле: 1 файл, ≤2 МБ, только `jpeg/png/webp`, превью `100x100`/`200x200` | аватар |
| `published` | bool, по умолчанию `false` | публиковать ли профиль гостям |
| `created_at`/`updated_at` | автодаты | контракт дат |

Принципы:

- `users` остаётся тощим: ключ-почта, роль, бан. Всё публичное и
  «человеческое» — в профиле. Так GDPR-стирание (`users.erase`)
  чистит персональное одним местом (добавить удаление профиля в
  `EraseUser`).
- Профиль **опционален и по умолчанию скрыт** (`published = false`):
  публичность — действие юзера, а не состояние по умолчанию. Иначе
  принятый риск перечисления ключей (L9) получает удобную витрину.
- Аватар отдаётся штатным файловым эндпоинтом, который проверяет
  **правило просмотра коллекции** — доступ к файлу наследует матрицу
  шага 2 без отдельного кода. Хранение: локальный диск либо
  S3-совместимое (настройка `files.s3`, можно тот же R2, что у
  бэкапов). Литестрим реплицирует только SQLite: папку `storage/`
  бэкапить отдельным правилом (или сразу держать в S3).
- Служебные/личные данные (бан, роль, сессии, адрес) в профиль НЕ
  попадают — их видят только свои и администраторы через другие
  чтения (шаг 3).

## Шаг 2 — механизм полей по ролям: маски в хендлерах, не правила

Правила коллекций фильтруют СТРОКИ, а не поля; «скрытые» поля PB —
бинарные (суперюзер против всех). Ролевое деление полей делается в
обработчиках гейтвея (проектный паттерн: так уже собраны `/sessions`,
`/deleted`, `/impact`):

- общий помощник «маска полей»: роль → разрешённый набор полей;
- маска применяется в каждом чтении гейтвея; суперюзер видит всё;
- матрица — единая точка, её легко проверить тестом и описать в
  документации.

Матрица видимости профиля:

| Данные | Гость | Юзер | Модератор | Админ (роль) | Суперюзер |
|---|---|---|---|---|---|
| Профиль: имя/аватар/био при `published` | ✔ | ✔ | ✔ | ✔ | ✔ |
| Профиль: непубликованный | ✖ | свой | ✔ | ✔ | ✔ |
| `users`: роль, созданный | ✖ | ✖ | ✔ | ✔ | ✔ |
| `users`: бан-поля | ✖ | ✖ | ✖ | ✔ | ✔ |

## Шаг 3 — чтения гейтвея (по каждой таблице без GET)

| Таблица | Чтение | Кому |
|---|---|---|
| `user_profiles` | `GET /api/seed/profile/{public_key}`, `GET /api/seed/profiles` (список/поиск, курсор), `PATCH /api/seed/profile` (свой) | профиль — по матрице шага 2 |
| `seed_sessions` | свой список уже есть; добавить `GET /api/seed/sessions/all` с маской полей | админ (роль) и суперюзер |
| `seed_settings` | личные — уже через `/policy`; добавить `GET /api/seed/settings` (все строки) | админ (роль) и суперюзер |
| `seed_gateway` | уже есть (`/gateway-config`) | админ (роль) и суперюзер |
| `seed_audit` | уже есть штатным списком | админ (роль) и суперюзер |
| `seed_challenges`, `seed_used` | **не нужны**: одноразовые нонсы и надгробия, живут минуты, читать нечего; суперюзеру доступны в панели | — |

Каждое новое чтение: маска полей, курсорная пагинация, запись в
журнал только действий (чтения не логируются — действующее правило).

## Шаг 4 — персональные данные и «другая база»

Факт: **PocketBase умеет только одну SQLite-базу** на инстанс; второй
подключения/внешние источники штатно не поддерживаются (проверено по
исходникам v0.40.4). Варианты по возрастанию цены:

1. **Одна база, разные коллекции** (рекомендация для старта): публичное
   в `user_profiles`, чувствительное в `users`/`seed_sessions`;
   бэкап уже литестримом в R2 — при желании профили бэкапятся тем же
   потоком, а личное — отдельным правилом хранения.
2. **Шифрование полей**: личный контент профиля шифруется ключом
   сервера перед записью; утечка файла базы не раскрывает данные.
   Добавляет управление ключом (окружение/ротация).
3. **Отдельный инстанс-хранилище**: второй PocketBase как «личный
   контур», гейтвей проксирует в него запросы. Физическое разделение
   есть, цена — вторая база, репликация, согласованность. Нужно,
   только если разделение — юридическое требование.

Решение сейчас: пункт 1; пункт 2 добавить, если появится требование
«персональные не должны читаться из файла базы». Архитектура шагов 1–3
этому не мешает (личные данные и так собраны в отдельных коллекциях).

## Порядок реализации (когда будет дана команда)

1. `user_profiles` в реестре схемы + связь с `users` + удаление
   профиля в `EraseUser`.
2. Помощник масок полей + тест на матрицу видимости.
3. Эндпоинты профиля (чтение, список с курсором, правка своего) +
   тесты: гость видит только `published`, чужой непубликованный —
   404, правка чужого — 403.
4. Админские чтения `sessions/all` и `settings` (если нужны к этому
   же релизу).
5. Тесты прав для каждой маски, обновление `README.md`
   (эндпоинты профиля и матрица видимости).

## Что намеренно НЕ входит

- создание профиля администратором за юзера (профиль — только
  руками владельца);
- история правок профиля (аудит действий и так фиксирует правки);
- перенос существующих данных `users` в профиль (данных там нет,
  кроме ключа и служебных полей).
