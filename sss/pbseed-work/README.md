# pbseed

Самодостаточный [PocketBase](https://pocketbase.io) с вкомпилированной
аутентификацией **seed (ed25519)**: вход по подписи челленджа приватным
ключом вместо пароля. Клиент хранит ключ (это и есть «пароль»), сервер не
хранит ничего, что позволило бы его восстановить.

Схема: **челлендж → подпись → вход**. На входе выдаются короткоживущий
токен доступа (15 минут) и долгоживущая httpOnly-кука сессии (30 дней).
Каждый запрос с токеном пользователя обязан нести живую куку сессии —
токен без куки бесполезен.

---

## Особенности проекта

- **Аутентификация по подписи.** ed25519-подпись сообщения
  `surreal-auth-v1:<домен>:<назначение>:<открытый ключ>:<нонс>`.
  Подпись привязана к домену экземпляра: подпись, созданная для одного
  сервера, не пройдёт на другом. Нонс одноразовый (уникальный индекс,
  сгорает до проверки подписи — перебор и повтор исключены).
- **Двухфакторность на уровне транспорта.** Токен доступа сам по себе не
  даёт доступа: промежуточный слой требует живую куку сессии на каждом
  запросе. Украденный токен без куки отклоняется (401).
- **Устройства и сессии.** Каждый вход — отдельная сессия (устройств
  сколько угодно). Список сессий с маской IP, страной, историей смен
  адреса и флагом «текущая»; отзыв одного устройства, выход и выход
  со всех устройств (один запрос к базе независимо от числа сессий).
- **Контроль смены IP.** Адрес соединения хранится как маска
  (`85.76.*.*`) и HMAC-хэш — сырые адреса не сохраняются и нигде не
  отдаются. При смене адреса на продлении: политика «выгонять» убивает
  сессию, иначе старая маска и страна пишутся в историю сессии
  (до 10 записей), сессия принимает новый адрес. Политика двухуровневая:
  персональная настройка → глобальная → выключена.
- **Баны.** Поля `banned`/`ban_reason`/`banned_until` проверяются при
  входе, продлении и на каждом запросе; срок истекает лениво —
  планировщик не нужен. Бан мгновенный: не нужен повторный вход, чтобы
  его «почувствовать».
- **Геолокация.** Локальная база MaxMind-формата (DB-IP Country Lite):
  страна пишется при создании сессии и обновляется при каждой смене
  адреса. Обновление базы — фоновая задача администратора с прогрессом,
  проверкой файла и атомарной подменой; защита от запросов к внутренним
  адресам на каждом переходе, включая редиректы.
- **Мягкое удаление и GDPR.** Сессии при удалении помечаются `deleted_at`
  (физическая очистка через 30 дней), восстановление в первые 30 секунд
  доступно владельцу, позже — администратору. Анализ ссылок
  «кто ссылается на запись», физическое удаление, список удалённых и
  GDPR-стирание пользователя (анонимизация + очистка данных) — отдельные
  административные эндпоинты.
- **Единый контракт времени.** Все коллекции сервиса несут
  `created_at`/`updated_at` (автодата) и `deleted_at` (метка удаления).
  Для сессий обычная активность двигает только `last_seen` —
  `updated_at` меняется лишь при реальных изменениях данных (адрес,
  страна, история, отзыв).
- **Схема — самовосстанавливающаяся.** Все служебные коллекции описаны
  в одном месте — реестре `schema_registry.go`. На каждом запуске
  состояние базы приводится к реестру: недостающие коллекции и поля
  добавляются (без удаления данных), индексы подтверждаются, правила
  доступа служебных коллекций восстанавливаются из реестра с записью
  в лог, старые имена полей мигрируются — обновления версии не требуют
  ручных действий. Базовые ролевые правила коллекции `users` тоже
  описаны в реестре и приводятся к нему на каждом старте.
- **Роли.** У пользователей роли `user`/`moderator`/`admin` (колонка
  `role`): модератор читает всех, админ модерирует; назначает роли
  консоль и суперюзер, а среди ролевых админов повышать до `admin`
  может только «админ+» — самый ранний по дате создания админ,
  защищённый от бана и смены роли всеми, кроме суперюзера
  (`adminplus.go`). Маска администратора — подпись:
  исполнитель действует своими правами, а действие помечается «от
  чьего имени».
- **Журнал действий — слежка за всеми.** В `seed_audit` пишется каждое
  действие через API независимо от прав: входы и регистрации (и
  неудачные — с причиной, включая входы суперюзера в панель), правки
  записей любыми ролями включая суперюзера из панели (список
  изменённых полей), операции с самими коллекциями и их правилами из
  панели, личные и глобальные политики, выходы и отзывы сессий,
  восстановления, баны, стирания, маски. Покрыты все три точки входа —
  гейтвей `/api/seed/*`, панель БД и штатный REST (см. «Точки входа
  аудита»). Под маской строка несёт «от чьего имени». Отказы и ошибки в
  строки записей не попадают; действия под маской и системная возня
  (продление активности, сборка мусора) не логируются. Журнал
  неизменяем: удалить или исправить строку не может никто, включая
  суперюзера, — стирает только фоновая очистка. Срок хранения вечный
  по умолчанию (`SEED_AUDIT_KEEP_DAYS` — дни, не меньше недели).
  Ключи действий и примеры чтения — в разделе «Журнал действий».
- **Фаервол панели на журнале.** Неудачные входы суперюзера (панель и
  REST — одни эндпоинты) считаются по строкам журнала: порог неудач
  временно блокирует адрес, порог блокировок за сутки отключает панель
  до конца суток. Суточное отключение снимается только консолью
  сервера, временная блокировка — консолью или суперюзером с рабочей
  сессией. Подробнее — в разделе «Фаервол панели».
- **Защита гейтвея.** Лимит регистраций с адреса и входов аккаунта в
  сутки, запирание адреса за неудачи входа подряд; регистрацию, вход и
  продление сессии можно отключить по отдельности. Стандартные пороги
  — константы; суперюзер или роль `admin` переопределяет их через базу
  без перезапуска (`/api/seed/gateway-config`), там же видна вся
  картина конфигурации (включая неизменяемые параметры). Все отказы
  пишутся в журнал. Подробнее — в разделе «Защита гейтвея».
- **Защита от флуда** включается автоматически на свежих установках
  (эндпоинты входа + стоковые пути); состояние логируется при каждом
  запуске.
- **Единый бинарник.** Один статический файл: встроенный веб-сервер,
  панель администратора (`/_/`), SQLite (чистый Go, без CGO).

> Демо-коллекция заметок в продукт не входит — она существует только
> в тестах.

## Как это работает

```
Клиент                                  Сервер
  │  POST /api/seed/challenge            │
  ├─────────────────────────────────────►│  выдаёт нонс (5 минут)
  │◄─────────────────────────────────────┤  {nonce}
  │  подпись = ed25519(ключ, сообщение)  │
  │  сообщение = "surreal-auth-v1:"      │
  │    + домен + ":" + назначение        │
  │    + ":" + открытый ключ + ":" + нонс│
  │  POST /api/seed/login                │
  ├─────────────────────────────────────►│  проверка подписи,
  │◄─────────────────────────────────────┤  токен (15 мин) + кука
  │                                      │  сессии (30 дней)
  │  запросы: токен + кука               │
  ├─────────────────────────────────────►│
  │  401 → POST /api/seed/renew (кука)   │
  ├─────────────────────────────────────►│  новый токен
```

Правило клиента: **любой 401 → один `renew` → один повтор запроса →
если снова 401, вести пользователя на вход по подписи**. Различать
«истёк токен» и «умерла сессия» заранее не нужно — `renew` сам ответит
401 (`revoked`/`no_session`), если сессия мертва.

Кук называется `pb_seed`, значение — `грант.секрет` (секрет хранится на
сервере только в виде SHA-256). Кука httpOnly, SameSite=Lax, флаг Secure
включён (отключается для локальной разработки по чистому HTTP).

## Быстрый старт (из исходников)

```sh
go build -o pbseed .
PB_SUPERUSER_EMAIL=admin@example.local PB_SUPERUSER_PASSWORD=change-me-123 \
SEED_DOMAIN=myapp.example SEED_IP_KEY="$(openssl rand -hex 32)" \
  ./pbseed serve --http=127.0.0.1:8090 --dir=./pb_data
```

Первый запуск сам создаст коллекции, закроет саморегистрацию по паролю
(единственный путь регистрации — вход по подписи) и создаст суперюзера из
переменных окружения. Панель администратора: `http://127.0.0.1:8090/_/`.

## Подключение с нуля: примеры

Все примеры — браузер/Node с `fetch`; кука httpOnly ходит сама при
`credentials: 'include'`. Для ed25519 используется библиотека
[`@noble/ed25519`](https://www.npmjs.com/package/@noble/ed25519)
(в браузере `Web Crypto` ed25519 есть не везде). Домен подписи
(`DOMAIN`) обязан совпадать с `SEED_DOMAIN` сервера.

### Общие помощники

```js
import * as ed from '@noble/ed25519';

const BASE   = 'https://api.example.com';   // локально: http://127.0.0.1:8090
const DOMAIN = 'myapp.example';             // = SEED_DOMAIN сервера

// Ключ клиента: создаётся один раз и хранится у пользователя.
// Это и есть «пароль» — потеря ключа = потеря доступа.
let secretKey = ed.utils.randomSecretKey();         // Uint8Array, 32 байта
const publicKey = ed.getPublicKey(secretKey);       // открытый ключ
const pk = Buffer.from(publicKey).toString('hex');  // 64 hex-символа

async function api(method, path, body, token) {
  const res = await fetch(BASE + path, {
    method,
    credentials: 'include',                          // возит куку pb_seed
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: token } : {}),
    },
    body: body ? JSON.stringify(body) : undefined,
  });
  const data = await res.json().catch(() => null);
  if (!res.ok) {
    const err = new Error(data?.error || res.status);
    err.status = res.status;
    throw err;
  }
  return data;
}

function signMessage(purpose, nonce) {
  const msg = `surreal-auth-v1:${DOMAIN}:${purpose}:${pk}:${nonce}`;
  return Buffer.from(ed.sign(msg, secretKey)).toString('hex');
}
```

### Регистрация (первый вход нового ключа)

```js
async function register(deviceName) {
  const { nonce } = await api('POST', '/api/seed/challenge',
    { public_key: pk, purpose: 'register' });
  const lg = await api('POST', '/api/seed/login', {
    public_key: pk,
    signature: signMessage('register', nonce),
    purpose: 'register',
    nonce,
    device_name: deviceName,          // например, «Ноутбук», до 200 символов
  });
  // Кука сессии уже установлена браузером.
  // Имена, начинающиеся с «@», зарезервированы сервером — 400
  // «reserved_device_name» (см. маску администратора ниже).
  return lg; // { access, session_id, user_id, expires_in: 900 }
}

let { access } = await register('Ноутбук');
```

### Вход существующего ключа

```js
async function login(deviceName) {
  const { nonce } = await api('POST', '/api/seed/challenge',
    { public_key: pk, purpose: 'login' });
  const lg = await api('POST', '/api/seed/login', {
    public_key: pk,
    signature: signMessage('login', nonce),
    purpose: 'login',
    nonce,
    device_name: deviceName,
  });
  return lg;
}
// Забаненный ключ получит 403 {error: 'banned', reason?}.
```

### Запросы с автоматическим продлением токена

```js
// Универсальная обёртка: 401 → один renew → один повтор.
async function authFetch(method, path, body) {
  try {
    return await api(method, path, body, access);
  } catch (e) {
    if (e.status !== 401) throw e;
    try {
      const rn = await api('POST', '/api/seed/renew', {}); // только кука
      access = rn.access;
    } catch {
      throw new Error('Сессия мертва — нужен вход по подписи');
    }
    return await api(method, path, body, access);
  }
}

// Пример: чтение своей записи пользователя.
const me = await authFetch('GET', '/api/collections/users/records/' + userId);
```

Ошибки продления: `401 no_session` (нет/неверна кука),
`401 revoked` (сессия отозвана или истекла), `401 ip_changed`
(адрес сменился при включённой политике — сессия убита, нужен вход
заново), `403 banned`.

### Список своих сессий

```js
const sessions = await authFetch('GET', '/api/seed/sessions');
for (const s of sessions) {
  console.log(
    s.device_name,            // имя устройства
    s.ip_masked,              // «85.76.*.*»
    s.country,                // код страны или ''
    s.last_seen,              // последняя активность
    s.created_at,             // когда создана
    s.current,                // эта сессия — текущая (из куки)
    s.revoked,                // отозвана
    s.history,                // [{event:'ip_changed', prev_masked, prev_country, at}]
  );
}
```

Необязательные параметры (неизвестные — 400):

| Параметр | Значение |
|---|---|
| `limit` | 1..100, по умолчанию 50 |
| `cursor` | курсор из заголовка `X-Next-Cursor` предыдущего ответа |
| `sort` | колонки через запятую, `-` — по убыванию: `created_at`, `updated_at`, `last_seen`, `expires`, `device_name`, `ip_country` (по умолчанию `-created_at`) |
| `revoked` | `true`/`false` — только отозванные/активные |
| `ip_country` | двухбуквенный код страны |
| `created_from`, `created_to` | диапазон `created_at` |
| `last_seen_from`, `last_seen_to` | диапазон `last_seen` |

```js
// Листание: заголовок X-Next-Cursor присутствует, пока есть страницы.
let cursor = '';
do {
  const res = await fetch(API + '/api/seed/sessions?limit=20' +
    (cursor ? '&cursor=' + encodeURIComponent(cursor) : ''), {
    headers: { Authorization: auth, Cookie: 'pb_seed=' + cookie },
  });
  const page = await res.json();
  cursor = res.headers.get('X-Next-Cursor') || '';
  // ...обработать страницу...
} while (cursor);
```

### Отзыв одного устройства, выход, выход со всех устройств

```js
// Убить конкретную сессию (например, «Телефон» из списка).
await authFetch('POST', '/api/seed/revoke', { grant_id: sessions[1].session_id });

// Выйти с текущего устройства (кука чистится).
await authFetch('POST', '/api/seed/logout', {});

// Выйти со всех устройств сразу (кука чистится).
const r = await authFetch('POST', '/api/seed/logout-all', {});
// r.revoked — сколько сессий отозвано
```

### Политика смены IP

Значение разрешения: персональная строка пользователя → глобальная →
`false` (не выгонять). Чтение доступно и гостю (глобальное значение —
для состояния переключателя на экране входа).

```js
// Прочитать действующее значение (автоматически область «свою»).
const p = await authFetch('GET', '/api/seed/policy');
// { key: 'kick_on_ip_change', value: false, source: 'me'|'global'|'default' }

// Гость читает глобальное значение по умолчанию.
const g = await api('GET', '/api/seed/policy?scope=global');

// Включить выгон при смене IP лично для себя.
await authFetch('POST', '/api/seed/policy', { value: true });              // scope=me

// Убрать персональную настройку (вернуться к глобальной).
await authFetch('DELETE', '/api/seed/policy');

// Администратор (суперюзер или роль "admin") управляет глобальным
// значением и замком:
//   POST /api/seed/policy {value:true, scope:'global', locked:true}
// locked запрещает пользователям СОЗДАВАТЬ персональные переопределения
// (редактировать свою существующую строку остаётся можно).
// Запись в глобальную область без прав администратора — 403.
```

### Роли пользователей

У каждого пользователя сайта есть роль — колонка `role` в таблице
`users`. Права даёт именно она, а не токен: токен лишь указывает на
запись, а правила и обработчики читают её роль.

| Роль | Права |
|---|---|
| `user` | только свои данные (по умолчанию при регистрации) |
| `moderator` | чтение всех пользователей (просмотр без изменений) |
| `admin` | модератор + бан, восстановление и жёсткое удаление записей, список удалённых, глобальные политики, маска администратора |

Суперюзер — отдельная сущность: это оператор сервера (панель `/_/`,
консоль), он выше любых правил и ролей не имеет. Администратор сайта —
обычный пользователь с ключом и `role = "admin"`.

Назначение роли — консольная команда (единственный способ сделать
первого администратора без входа на сайт; владельцу ключа даже не нужно
раньше бывать на сайте — запись создаётся заранее):

```bash
./pbseed user role <public_key> admin        # user | moderator | admin
```

После этого владелец ключа входит как обычно и сразу обладает ролью.
Сам себе юзер роль повысить не может (служебные поля охраняются, 403);
почту (открытый ключ) не меняет даже админ — только суперюзер.

Админ по роли назначает только `user` и `moderator` (и может понижать);
повысить до `admin` через API может только «админ+», суперюзер или
консоль — обычные админы не плодят админов.

**«Админ+» — защищённый первый админ.** Запись `users` с ролью
`admin`, созданная раньше всех остальных админов (среди живых; при
совпадении времени разбор по ид). Исключения для него собраны в
`adminplus.go` (`firstAdminID`/`isAdminPlus` — одно место определения,
новые исключения добавляйте через них):

- его нельзя забанить через REST никому, кроме суперюзера (консоль не
  ограничена — оператор выше ролевой иерархии);
- его роль нельзя изменить через REST никому, кроме суперюзера —
  иначе защиту обходили бы связкой «понизить, затем забанить»;
- он единственный из ролевых админов повышает до `admin`.

Если носитель выбывает (понижение, стирание, мягкое удаление), звание
переезжает к следующему по дате создания админу — защита всегда у
самого раннего из живых.

### Администрирование

Админские операции доступны двумя каналами:

- **суперюзер** — штатный вход панели
  (`POST /api/collections/_superusers/auth-with-password`,
  `{identity, password}`), ходит с заголовком `Authorization`, кука
  сессии не нужна, правила обходятся; это служебный канал оператора;
- **роль `admin`** — обычный вход по ключу; те же операции выполняются
  токеном юзера + его кукой сессии (как у любого пользователя).

```js
// suToken — токен суперюзера; для роли "admin" вместо него
// подставляется токен обычного входа и добавляется кука сессии.
async function admin(path, body, method = body ? 'POST' : 'GET') {
  return api(method, path, body, suToken);
}

// --- Геобаза -----------------------------------------------------------
// Запустить обновление (пустой url = официальный ежемесячный выпуск).
await admin('/api/seed/geo/update', {});
// Свой источник: { url: 'https://…/country.mmdb.gz' } — только http(s).

// Прогресс и сведения о загруженной базе (опрашивать до состояния 'ready').
const st = await admin('/api/seed/geo/status');
// { state:'idle'|'downloading'|'ready'|'error', percent, downloaded_bytes,
//   total_bytes, url, error, db: {release, sha256, bytes, downloaded_at} }

// Диагностическое определение страны.
const lk = await admin('/api/seed/geo/lookup?ip=8.8.8.8'); // {ip, country}

// --- Баны --------------------------------------------------------------
// Поля модерации в коллекции users редактируют суперюзер и роль "admin"
// штатным PATCH (обычному пользователю менять их запрещено, 403).
await admin(`/api/collections/users/records/${userId}`, {
  banned: true,
  ban_reason: 'нарушение правил',
  banned_until: '2027-01-01 00:00:00.000Z', // пусто = бессрочно
}, 'PATCH');
// Бан начинает действовать немедленно (проверяется на каждом запросе).

// --- Маска администратора (модель B: маска = подпись) -----------------
// Маска — это ПОДПИСЬ, а не смена личности. Исполнитель (суперюзер или
// роль "admin") надевает маску юзера и продолжает действовать СВОИМ
// токеном и со СВОИМИ правами: суперюзер может всё, админ — админское.
// Маска лишь фиксирует, от чьего имени ведётся работа: создаётся
// сессия маски с зарезервированным именем "@administrator" и полем
// «от чьего имени», а каждое действие пишется в журнал `seed_audit`.
// Целевой юзер при этом не затрагивается (токен ему не выпускается).
// Имена на "@..." обычным входам запрещены (400). Каждая маска пишется
// и в лог сервера, и в журнал.
const mask = await admin('/api/seed/impersonate', { user_id: userId });
// { access, session_id, masked_as, expires_in, masked: true } + кука.
// `access` — токен ИСПОЛНИТЕЛЯ (права его собственные), кука — сессия
// маски; дальше ходим ими, а действия записываются «от чьего имени».

// Снять маску: тот же эндпоинт с пустым телом (идёт отзыв сессии маски).
await admin('/api/seed/impersonate', {}); // { ok: true, unmasked: true }

// --- Мягкое удаление, восстановление, стирание -------------------------
// Список мягко удалённых записей коллекции — с курсорной пагинацией.
// Необязательные параметры (неизвестные — 400):
//   limit — 1..200 (по умолчанию 50);
//   cursor — из заголовка X-Next-Cursor предыдущего ответа;
//   sort — deleted_at | created_at | updated_at, «-» — по убыванию
//          (по умолчанию -deleted_at).
const deleted = await admin('/api/seed/deleted?collection=seed_sessions&limit=50');
// [{id, deleted_at, created_at, updated_at}, ...]
// Пока страницы есть, ответ несёт заголовок X-Next-Cursor.

// Физическое удаление в обход мягкого.
await admin('/api/seed/hard-delete', { collection: 'seed_sessions', ids: [id] });
// {ok: true, deleted: 1}

// Восстановление мягко удалённого. Суперюзер — всегда; обычный
// пользователь — только свои записи и только 30 секунд с момента
// удаления. Восстановленная сессия остаётся отозванной (нужен вход заново).
await admin('/api/seed/restore', { collection: 'seed_sessions', ids: [id] });
// {ok: true, restored: 1}

// Перед удалением — кто ссылается на запись.
const impact = await admin(`/api/seed/impact?collection=users&id=${userId}`);
// {target, references: [{collection, field, count}], total}

// GDPR-стирание: сессии и настройки удаляются физически, пользователь
// анонимизируется и помечается deleted_at.
await admin('/api/seed/erase', { user_id: userId }); // {ok: true}
```

### Журнал действий (`seed_audit`)

Журнал фиксирует каждое действие через API независимо от прав —
пишутся ВСЕ действующие лица: обычные юзера, модераторы, админы и
суперюзер из панели. В журнал ведёт ОДНА функция записи (сквозные хуки
на записи + события входа): никакие точки больше строки не пишут,
новая операция = один вызов. Записываются только СОСТОЯВШИЕСЯ операции
(отказы и ошибки валидации в строки не попадают; исключение — вход:
пишется и успех, и неудача). Системная возня (сборка мусора,
продление активности, правки самого журнала) не логируется.

Журнал неизменяем: создание, правка и удаление строк через API
запрещены ВСЕМ, включая суперюзера и панель (403 `audit_immutable`).
Пишет только сервер, удаляет только фоновая очистка — и лишь когда
задан срок хранения (`SEED_AUDIT_KEEP_DAYS`, не меньше недели).

Поля строки журнала:

| Поле | Содержание |
|---|---|
| `action` | ключ действия (таблица ниже) |
| `actor_id` | ид исполнителя (у гостей пусто) |
| `actor_kind` | уровень: `superuser`, `admin`, `moderator`, `user`, `guest` |
| `actor_label` | подпись: почта или открытый ключ |
| `on_behalf_of` | «от чьего имени», если действие под маской |
| `session` | ид сессии из `seed_sessions`, в которой сделано действие |
| `detail` | подробности (состав зависит от ключа) |
| `created_at` | когда произошло |

Каждая строка привязана к сессии, в которой сделано действие: у обычных
юзеров это их кука-сессия, у маски — маска-сессия, у суперюзера — его
собственная сессия в `seed_sessions` (имя `@superuser`, привязка по
хэшу носимого токена). Обновление токена суперюзера сессию не рвёт —
она продлевается тем же грантом, поэтому вся работа одного входа
панели собирается в одну сессию. У гостей и серверных строк фаервола
поле пустое (атрибуция — по `ip_hash`).

Ключи действий:

| Ключ | Что фиксирует | Состав `detail` |
|---|---|---|
| `auth.register` | регистрация нового ключа | `device`, `ip_masked`, `ip_hash`, `country` |
| `auth.login` | вход существующим ключом | то же |
| `auth.login_failed` | неудачный или заблокированный вход | `public_key`, `purpose`, `reason` |
| `auth.register_denied` | отказ защиты гейтвея в регистрации | `public_key`, `reason`, `ip_hash`, `ip_masked` |
| `auth.login_denied` | отказ защиты гейтвея во входе | `public_key`, `reason`, `ip_hash`, `ip_masked` |
| `auth.renew_failed` | неудачное продление токена | `grant`, `user_id`, `reason` |
| `auth.api_login` | штатный вход юзера (пароль/ОТП/OAuth2) | `collection`, `method`, `ip_masked` (для OAuth2 — `provider`) |
| `auth.api_login_failed` | неудачный штатный вход | `collection`, `identity`, `method`, `ip_masked` |
| `auth.api_refresh` | штатное продление токена юзера | `collection`, `ip_masked` |
| `session.revoke` | отзыв одного устройства | `grant_id` |
| `session.logout` | выход (текущая сессия) | `grant_id` |
| `session.logout_all` | выход со всех устройств | `revoked` — сколько отозвано |
| `records.create` | создание записи любой коллекции | `collection`, `id` |
| `records.update` | правка записи, включая панель | `collection`, `id`, `fields` — изменённые поля |
| `records.delete` | мягкое удаление записи | `collection`, `id` |
| `records.restore` | восстановление мягко удалённого | `collection`, `ids`, `restored` |
| `records.hard_delete` | физическое удаление в обход мягкого | `collection`, `ids`, `deleted` |
| `policy.set` | установка политики (личной или глобальной) | `key`, `value`, `scope` |
| `policy.delete` | удаление политики | `key`, `scope` |
| `gateway.config` | смена параметра защиты гейтвея через базу | `key`, `op` (`set`/`delete`), для `set` — `value`; у серверных хуков — ещё `hook` (имя хука) |
| `impersonate.start` | надета маска администратора | `target` — от чьего имени |
| `impersonate.stop` | маска снята | `target` |
| `users.erase` | GDPR-стирание пользователя | `user_id` |
| `geo.update` | обновление геобазы | `url` |
| `superuser.login` | успешный вход суперюзера (панель или REST) | `method`, `ip_masked`, `ip_hash` |
| `superuser.login_failed` | неудачный вход суперюзера | `identity`, `method`, `ip_masked`, `ip_hash` |
| `collections.create` | создание коллекции (из панели) | `collection`, `id` |
| `collections.update` | правка коллекции из панели | `collection`, `id`, `rules` — изменённые правила, `fields_added`/`fields_removed` |
| `collections.delete` | удаление коллекции | `collection`, `id` |
| `firewall.lock_ip` | фаервол заблокировал адрес | `ip_hash`, `ip_masked`, `until`, `fails` |
| `firewall.panel_off` | фаервол отключил панель до конца суток | `until`, `locks_today` |
| `firewall.unlock` | разблокировка | `what` (`ip`/`panel`), `by` (`api`/`console`), `ip_hash` |

Чтение журнала — суперюзером и пользователями с ролью `admin`
(коллекция закрыта для остальных; запись запрещена всем):

```js
// Аудит всего сайта: все строки, последние сверху.
const feed = await admin('/api/collections/seed_audit/records?perPage=100&sort=-created_at');

// «Что творил юзер»: все строки, где пользователь — исполнитель.
const did = await admin(
  '/api/collections/seed_audit/records?sort=-created_at' +
  '&filter=' + encodeURIComponent(`actor_id="${userId}"`));

// «Что творили у юзера»: действия под маской от его имени и любые
// операции с его записями (его ид в `detail`).
const mention = encodeURIComponent(`on_behalf_of="${userId}" || detail.id="${userId}"`);
const doneTo = await admin(
  '/api/collections/seed_audit/records?sort=-created_at&filter=' + mention);

// «Что было в сессии»: все действия одной сессии (грант виден в списке
// сессий или в самой строке журнала).
const perSession = await admin(
  '/api/collections/seed_audit/records?sort=-created_at' +
  '&filter=' + encodeURIComponent(`session="${grantId}"`));
```

### Точки входа аудита

У сайта три двери — журнал покрывает все:

| Точка входа | Что это | Что пишется |
|---|---|---|
| **Гейтвей** | служебные эндпоинты `/api/seed/*`: вход по ключу эц25519, сессии, политики, маски, геобаза, операции мягкого удаления | `auth.login/register/login_failed/renew_failed`, отказы защиты `auth.register_denied/login_denied`, `session.*`, `policy.*`, `impersonate.*`, `records.restore`, `records.hard_delete`, `users.erase`, `geo.update` |
| **Панель БД** | дашборд `/_/`: вход суперюзера, правка записей любых коллекций, создание/удаление коллекций и их правил | `superuser.login/login_failed`, `firewall.*`, `records.create/update/delete`, `collections.create/update/delete` |
| **REST** | штатный API PocketBase `/api/collections/…`: CRUD любой коллекции любым действующим лицом, штатные входы юзеров и продление токенов | `records.*`, `auth.api_login`, `auth.api_login_failed`, `auth.api_refresh` |

Панель и REST делят одни эндпоинты (панель — клиент штатного API),
поэтому хуки пишутся один раз и покрывают обе точки. Штатный вход
юзеров (пароль/ОТП/OAuth2) существует рядом с гейтвеем и тоже
наблюдается; штатное продление токена без куки сессии дальше
мидлвары сессий не проходит. Входы суперюзера (панель и REST — одни
эндпоинты) дополнительно охраняет фаервол (см. ниже).

### Опции аудита

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SEED_AUDIT_KEEP_DAYS` | вечно | срок хранения журнала в днях: пусто/0 = вечно, меньше 7 округляется до недели; удаляет только фоновая очистка |
| `SEED_GC_EVERY` | `5m` | период фоновой очистки (истёкшие сессии и челленджи + срок журнала) |
| `SEED_FIREWALL` | включён | фаервол на журнале: `0`/`false`/`off`/`no` выключает меры, аудит входов остаётся |
| `SEED_FIREWALL_FAILS` | `5` | неудачных входов суперюзера с адреса для временной блокировки |
| `SEED_FIREWALL_WINDOW` | `15m` | окно наблюдения за неудачными входами |
| `SEED_FIREWALL_LOCK` | `30m` | срок временной блокировки адреса |
| `SEED_FIREWALL_BLOCKS` | `3` | блокировок адресов за сутки для отключения панели до конца суток |

### Как добавить событие в журнал

**Новая таблица со штатным CRUD не требует ничего.** Создайте
коллекцию в панели или через `POST /api/collections` — её создание,
правки и удаление записей будут писаться автоматически: сквозные хуки
покрывают любую коллекцию, кроме самого журнала и служебных таблиц.

**Новый служебный эндпоинт** — один вызов после успешного выполнения
операции:

```go
func seedReport(e *core.RequestEvent) error {
	// ... дело ...
	if err := e.App.Save(rec); err != nil {
		return seedErr(e, 500, "store_failed")
	}
	// Исполнитель, сессия и маска разрешатся сами.
	auditLog(e, "report.create", map[string]any{"id": rec.Id})
	return e.JSON(200, map[string]any{"ok": true})
}
```

Правила:

- писать только после **состоявшейся** операции (`err == nil`); отказы
  в строки записей не попадают (исключение — события входа, их пишут и
  неудачными: `auditLogAs(e, nil, "auth.api_login_failed", …)`);
- ключ действия — строчный, вида `область.глагол` (`policy.set`,
  `session.revoke`, `geo.update`);
- `detail` — словарь подробностей, которые понадобятся разбору
  инцидентов (ид записей, список полей, причина);
- серверное действие без запроса (фаервол, фоновые процессы) пишется
  низко: `auditWriteRow(app, actor, "", "", "action", detail)`;
- чтения (списки, просмотр) не аудируются — журнал фиксирует действия,
  а не взгляды.

### Фаервол панели

Журнал — не только летопись, но и источник решений фаервола: по его
строкам считаются неудачные входы суперюзера и принимаются меры.
Покрываются обе двери в панель: интерфейс «/_/» и REST-авторизация
суперюзера (`auth-with-password`, одноразовый код, OAuth2 — это одни
и те же эндпоинты для панели и для API).

Два уровня защиты:

1. **Временная блокировка адреса.** Порог неудачных входов с одного
   адреса за окно наблюдения (`SEED_FIREWALL_FAILS`, `SEED_FIREWALL_WINDOW`)
   блокирует адрес на `SEED_FIREWALL_LOCK`. Даже верный пароль
   заблокированного адреса не пускается (403 `firewall_locked`).
2. **Суточное отключение панели.** Порог блокировок адресов за сутки
   (`SEED_FIREWALL_BLOCKS`) отключает вход суперюзера и интерфейс «/_/»
   до конца суток (403 `panel_off`).

Снятие блокировок:

- временную блокировку адреса снимает **консоль сервера**
  (`pbseed firewall unlock-ip [IP]`, без аргумента — все адреса) или
  **суперюзер с рабочей сессией** через
  `POST /api/seed/firewall/unlock` (`{ip: "1.2.3.4"}`);
- суточное отключение панели снимается **только консолью**
  (`pbseed firewall unlock-panel`) — через API его снять нельзя
  (403 `console_only`);
- `pbseed firewall status` показывает состояние: отключена ли панель,
  активные блокировки адресов, пороги.

Все события фаервола пишутся в тот же `seed_audit` (`superuser.login`,
`superuser.login_failed`, `firewall.lock_ip`, `firewall.panel_off`,
`firewall.unlock`) — историю атаки нельзя подделать или затереть:
журнал неизменяем. Адрес в журнале — только хэш и маска, сырой адрес
не хранится. Отключить фаервол целиком: `SEED_FIREWALL=0`
(аудит входов при этом остаётся).

```js
// Состояние фаервола (только суперюзер).
const fw = await admin('/api/seed/firewall/status');
// { enabled, panel_off_until, locks_today, active_locks: [{ip_masked, until}], limits }

// Снять временную блокировку адреса (суперюзер с рабочей сессией).
await admin('/api/seed/firewall/unlock', { ip: '203.0.113.7' }); // {ok: true}
// {what:'panel'} здесь не сработает — только консоль сервера.
```

### Защита гейтвея

Вход по ключу, регистрация и продление сессии охраняются отдельно от
фаервола панели. Как и фаервол, защита читает журнал и пишется в него
же: **каждый отказ фиксируется строкой журнала** — защита не создаёт
слепых мест в наблюдении.

Меры (стандартные пороги — константы кода):

1. **Лимит регистраций с адреса.** Не более `reg_per_day` аккаунтов в
   сутки с одного адреса (стандарт 2; 403 `register_limit`).
2. **Лимит входов аккаунта.** Не более `logins_per_day` входов в сутки
   на один аккаунт (стандарт 100; 403 `login_limit`).
3. **Запирание за неудачи подряд.** Счётчик неудач — ОДИН НА АДРЕС,
   а не на ключ: ключ либо зарегистрирован либо нет, и поключевой
   счётчик не поймал бы ни перебор сидов (много разных ключей с одного
   адреса), ни прыжки между аккаунтами с неверными подписями. Порог
   `max_fails` неудач подряд с одного адреса (стандарт 10) запирает
   адрес на срок `fail_lock` (стандарт 15 минут; 403
   `failures_locked`): с запертого адреса не пускается ни один ключ,
   даже с верной подписью. Неудачей считается: неверная подпись, вход
   незарегистрированным ключом, повторная регистрация существующего
   ключа, имя устройства из служебного пространства, вход забаненного.
   Успешный вход с адреса обнуляет счётчик; по истечении срока
   запирания адрес пробует снова, а новая неудача запирает его заново.
4. **Независимые выключатели.** Регистрацию (`register`), вход
   (`login`) и продление сессии (`renew`) можно отключить по
   отдельности (403 `register_disabled` / `login_disabled` /
   `renew_disabled`). Всё прочее продолжает работать.

Каждый параметр разрешается в порядке: **запись в базе → переменная
окружения → константа**.

**Настройка через базу (без перезапуска).** Эндпоинты
`/api/seed/gateway-config` доступны **суперюзеру и роли `admin`**
(ролевой админ — обычный пользователь и приходит с кукой сессии).
Записать можно только значение, **отличающееся от стандартного**
(равное отклоняется: 400 `default_value`) — база хранит только
переопределения, откат к стандарту выполняется удалением строки.
Смена настройки фиксируется журналом (`gateway.config`).

```js
// Полная картина конфигурации: переопределяемые параметры (значение,
// источник, стандарт) и неизменяемые (значение, место установки).
const cfg = await admin('/api/seed/gateway-config');
// cfg.params   — [{key, value, source, default, env}]
// cfg.readonly — [{key, value, where}] (окружение / только при запуске)

// Переопределить: выключить регистрацию и поднять лимит входов.
await admin('/api/seed/gateway-config', { key: 'register', value: false });
await admin('/api/seed/gateway-config', { key: 'logins_per_day', value: 200 });
await admin('/api/seed/gateway-config', { key: 'fail_lock', value: '30m' });

// Вернуть к стандарту (окружение/константа) — удалением строки.
await admin('/api/seed/gateway-config?key=register', null, 'DELETE');
```

Коллекция `seed_gateway` видна в панели как обычная таблица
(строки-переопределения), но штатный путь — эндпоинты: они проверяют
права, значение и пишут журнал.

**Программный доступ (для хуков).** Серверный код читает и меняет
конфиг тем же ядром — аналог `{get, set} = useSettings()`:

```go
value, source, ok := settingsGet(app, "reg_per_day") // база → окружение → константа
if _, err := settingsSet(app, "max_fails", 5); err != nil {
	// errSettingsKey / errSettingsValue / errSettingsDefault
}
settingsDelete(app, "max_fails") // откат к стандарту
```

Аудит изменений:

- смена через эндпоинты пишется с исполнителем (суперюзер/админ) —
  `auditLog`;
- хуки меняют конфиг обёртками `settingsSetByHook(app, "имя_хука", …)`
  и `settingsDeleteByHook` — строка журнала несёт имя хука в
  `detail.hook` (исполнитель-человек у серверного действия отсутствует,
  атрибуция — по этому полю);
- чистые `settingsSet`/`settingsDelete` журнала не пишут — аудит
  остаётся за вызывающим (эндпоинт или обёртка хука); неудачная запись
  (равная стандарту, мусор) в журнал не попадает.

На этом механизме уже работают хуки автоматизации (`automation.go`):

- **autotune** — предохранитель гейтвея: если переопределением в базе
  `reg_per_day` поднят выше предела (50), строка сразу снимается
  `settingsDeleteByHook(app, "autotune", …)` — строка журнала несёт
  `detail.hook: autotune`. Встроен во все три пути записи конфига:
  штатный REST коллекции, эндпоинт `/api/seed/gateway-config` и
  консольную команду `gateway set`;
- **каскад бана** — бан через REST (`users.banned = true`) немедленно
  отзывает все живые сессии забаненного одним запросом к базе и пишет
  в журнал `session.kill` (`detail`: пользователь, число отзывов,
  `reason: ban_cascade`). Правка уже забаненного без отзывов
  (например, смена причины) строку не создаёт — дублей не бывает.
  Консольный бан отзыва не требует: забаненного останавливает
  бан-проверка сессионной мидлвары на любом запросе и проверка при
  продлении сессии.

Переменные окружения (`SEED_REGISTER`, `SEED_LOGIN`, `SEED_RENEW`,
`SEED_GATEWAY_REG_PER_DAY`, `SEED_GATEWAY_LOGINS_PER_DAY`,
`SEED_GATEWAY_MAX_FAILS`, `SEED_GATEWAY_FAIL_LOCK`) остаются
прослойкой между базой и константой и удобны для развёртывания.

Отказы пишутся в `seed_audit` ключами `auth.register_denied` и
`auth.login_denied` (`detail`: ключ, причина, хэш и маска адреса);
отказ продления — тем же `auth.renew_failed` с причиной
`renew_disabled`. Лимиты считаются по строкам журнала за текущие
сутки — защита не хранит отдельных счётчиков.

### Курсорная пагинация записей

Рядом со штатным списком записей работает курсорный режим —
`GET /api/collections/{коллекция}/records/cursor`. Права и язык
`?filter=` — ровно штатные; штатный `/records` (страницы `page`/`perPage`)
не меняется. Курсор устойчив к вставкам и удалениям между страницами и
не использует `OFFSET`.

```js
// Параметры: filter (язык штатного API), sort (колонки через запятую,
// «-» — по убыванию; по умолчанию created), limit (1..200, по умолчанию
// 30), cursor, with_total=1 (добавить totalItems отдельным COUNT).
let cursor = '';
do {
  const page = await admin(
    '/api/collections/seed_sessions/records/cursor' +
    '?filter=revoked=false&sort=-created_at&limit=50' +
    (cursor ? '&cursor=' + encodeURIComponent(cursor) : ''),
  );
  // page.items — записи в штатном формате;
  // page.nextCursor — null, когда страниц больше нет.
  cursor = page.nextCursor || '';
} while (cursor);
```

Для коллекций с мягким удалением скрытые записи не выдаются
не-суперюзеру и в курсорном режиме.

Гибридный мостик: если у штатного `/records` задана явная `?sort=` из
простых колонок и есть следующая страница, ответ дополнительно несёт
заголовок `X-Next-Cursor` — по нему можно продолжить листание уже
курсорным режимом с тем же фильтром и сортировкой. Тело штатного
ответа при этом не меняется.

### Источник IP: как переключить на заголовок

Весь сервис определяет адрес клиента штатным `RealIP()`: от него
считаются `ip_hash` в журнале, блокировки фаервола и счётчики
гейтвея «на адрес». Источник адреса — это настройка доверенного
прокси, меняется без перезапуска и без правки кода.

На этапе сборки/деплоя источник задаётся переменной окружения
`PROXY_HEADERS` (заголовки через запятую, например
`CF-Connecting-IP`): первый старт свежей базы сеет её в настройку
доверенного прокси. Уже настроенную базу переменная не
перезаписывает — ею управляют панель или запрос ниже.

Механика: перебираются заголовки из списка `trustedProxy.headers`
в порядке перечисления; из найденного значения берётся последний
записанный прокси адрес (для списков вида `X-Forwarded-For` —
правый, как добавленный доверенным прокси; левый брать нельзя —
его может дописать сам клиент). Если ни один заголовок не дал
адрес — используется адрес соединения.

Способы переключения:

1. **Панель** — `/_/` → Settings → «Trusted Proxy», вписать имена
   заголовков.
2. **Запросом** (токен суперюзера; это слияние — остальные
   настройки не затираются):

```bash
curl -X PATCH https://service.example/api/settings \
  -H "Authorization: <токен суперюзера>" \
  -H "Content-Type: application/json" \
  -d '{"trustedProxy": {"headers": ["CF-Connecting-IP"]}}'
```

Для Cloudflare достаточно одного `CF-Connecting-IP` — он несёт ровно
один адрес клиента, поэтому порядок выбора в списке не играет роли
(для `X-Forwarded-For` остаётся поведение «правый адрес»; флаг
`useLeftmostIP` не включать).

**Предварительное условие.** Доверять заголовку можно только тогда,
когда запрос не способен прийти в обход прокси. Проверка подлинности
границы — сравнение токена/заголовка с тем, что присылает
Cloudflare, против доменов, настроенных у сервиса, — живёт на самой
границе (туннель, разрешённые диапазоны, сертификаты origin-pull);
сервис заголовки не проверяет, он лишь переключает источник адреса.
Не включайте заголовок, пока прямой доступ к порту не закрыт: любой
клиент начнёт подделывать адрес и обходить лимиты «на адрес».

Проверка: `GET /api/health` с токеном суперюзера возвращает
`realIP` — пришлите запрос с настроенным заголовком и убедитесь, что
адрес взят из него. Рабочий признак в журнале (`audit tail`):
`ip_masked` и `ip_hash` строк считаются из заголовка, а не из адреса
соединения.

## Сборка под Docker

### Базовый образ

```sh
docker build -t pbseed .
docker run -d --name pbseed -p 8090:8090 \
  -v pbseed_data:/pb/pb_data \
  -e PB_SUPERUSER_EMAIL=admin@example.local \
  -e PB_SUPERUSER_PASSWORD=change-me-123 \
  -e SEED_DOMAIN=myapp.example \
  -e SEED_IP_KEY="$(openssl rand -hex 32)" \
  pbseed
```

Многоступенчатая сборка даёт статический бинарник в образе `alpine`
(без CGO — SQLite на чистом Go). Данные живут в томе `/pb/pb_data`;
без тома каждый перезапуск начинает с пустой базы (суперюзер создастся
заново из переменных, пользователи зарегистрируются теми же ключами).

Пример `docker-compose.yml`:

```yaml
services:
  pbseed:
    build: .
    ports: ["8090:8090"]
    environment:
      PB_SUPERUSER_EMAIL: admin@example.local
      PB_SUPERUSER_PASSWORD: change-me-123
      SEED_DOMAIN: myapp.example
      SEED_IP_KEY: 0123456789abcdef0123456789abcdef
      SEED_GC_EVERY: 5m
    volumes:
      - pbseed_data:/pb/pb_data
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8090/api/health"]
      interval: 30s
      timeout: 5s
      retries: 3

volumes:
  pbseed_data:
```

### Образ с репликацией в Cloudflare R2 (для эфемерных дисков)

`Dockerfile.r2` добавляет сайдкар [litestream](https://litestream.io):
каждое изменение базы устремляется в R2 (~1 секунда), а при старте на
пустом диске база восстанавливается из реплики. Если переменные `R2_*`
не заданы, образ работает как обычный (эфемерный диск).

```sh
docker build -f Dockerfile.r2 -t pbseed:r2 .
docker run -d -p 8090:8090 \
  -e PB_SUPERUSER_EMAIL=admin@example.local \
  -e PB_SUPERUSER_PASSWORD=change-me-123 \
  -e SEED_DOMAIN=myapp.example \
  -e R2_ACCOUNT_ID=… -e R2_BUCKET=pbseed \
  -e R2_ACCESS_KEY_ID=… -e R2_SECRET_ACCESS_KEY=… \
  pbseed:r2
```

Настройка R2: создать бакет, выдать токену права чтения/записи объекта
(без админских прав), добавить четыре переменные. Реплика покрывает
только `data.db` (пользователи, сессии, настройки); геобаза
перекачивается заново одной кнопкой (`POST /api/seed/geo/update`),
префикс реплики в бакете — `pbseed/`.

> **Один экземпляр.** Не масштабируйте сервис до двух и более реплик на
> один бакет: два писателя разветвят базу. Если нужен настоящий том —
> используйте обычный образ с томом (или этот же образ как внешнюю
> резервную копию, всё равно одним экземпляром).

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PB_SUPERUSER_EMAIL` | — | почта первого суперюзера (создаётся, только если его ещё нет) |
| `PB_SUPERUSER_PASSWORD` | — | пароль суперюзера (минимум 8 символов) |
| `SEED_DOMAIN` | `seed.local` | домен-привязка подписи; **обязан совпадать** со значением клиента |
| `SEED_IP_KEY` | не задан | ключ HMAC для хэшей адресов; без ключа используется устаревший SHA-256 (при старте — предупреждение). Задайте случайные 32+ байта |
| `PROXY_HEADERS` | `X-Forwarded-For` | список доверенных заголовков прокси через запятую (источник реального IP); сеется при первом старте свежей базы, настроенную базу не трогает |
| `SEED_GC_EVERY` | `5m` | период фоновой очистки (челленджи, нонсы, истёкшие сессии, мягко удалённые старше 30 дней) |
| `SEED_AUDIT_KEEP_DAYS` | вечно | срок хранения журнала действий в днях: пусто/0 = вечно, значения меньше 7 округляются до недели; удаляет только фоновая очистка |
| `SEED_FIREWALL` | включён | фаервол панели по журналу; `0`/`false`/`off`/`no` — выключить (аудит входов остаётся) |
| `SEED_FIREWALL_FAILS` | `5` | неудачных входов суперюзера с адреса для временной блокировки |
| `SEED_FIREWALL_WINDOW` | `15m` | окно наблюдения за неудачными входами |
| `SEED_FIREWALL_LOCK` | `30m` | срок временной блокировки адреса |
| `SEED_FIREWALL_BLOCKS` | `3` | блокировок адресов за сутки для отключения панели до конца суток |
| `SEED_REGISTER` | включён | выключатель регистрации новых ключей: `0`/`false`/`off`/`no` — отключить (403 `register_disabled`). Переопределяется через БД: `/api/seed/gateway-config` |
| `SEED_LOGIN` | включён | выключатель входа существующих ключей: `0`/`false`/`off`/`no` — отключить (403 `login_disabled`). Переопределяется через БД |
| `SEED_RENEW` | включён | выключатель продления сессии: `0`/`false`/`off`/`no` — отключить (403 `renew_disabled`). Переопределяется через БД |
| `SEED_GATEWAY_REG_PER_DAY` | `2` | регистраций в сутки с одного адреса сверх — 403 `register_limit`. Переопределяется через БД |
| `SEED_GATEWAY_LOGINS_PER_DAY` | `100` | входов аккаунта в сутки сверх — 403 `login_limit`. Переопределяется через БД |
| `SEED_GATEWAY_MAX_FAILS` | `10` | неудач входа подряд с одного адреса для запирания адреса. Переопределяется через БД |
| `SEED_GATEWAY_FAIL_LOCK` | `15m` | срок запирания адреса после порога неудач. Переопределяется через БД |
| `PB_COOKIE_INSECURE=1` | выключено | только для разработки по HTTP: снимает флаг `Secure` с куки (при старте — предупреждение) |
| `SEED_GEO_ALLOW_PRIVATE=1` | выключено | только для тестов: разрешить геобазу с локальных/приватных адресов |
| `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | — | Cloudflare R2 для litestream (только образ `Dockerfile.r2`) |
| `SEED_TEST_DOMAIN` | `seed.local` | только тестовый сьют: должен совпадать с `SEED_DOMAIN` сервера |

## Схема БД

Единый источник истины — реестр в `schema_registry.go`: коллекции,
поля, индексы, флаги мягкого удаления, правила доступа. При каждом
запуске база приводится к реестру:

- отсутствующая коллекция создаётся;
- отсутствующее поле добавляется (данные никогда не удаляются);
- правила доступа служебных коллекций восстанавливаются из реестра
  с записью в лог;
- индексы подтверждаются физически (идемпотентно);
- легаси-поле `deleted` переименовывается в `deleted_at`.

Добавление поля или коллекции — одна правка `schema_registry.go`.
Там же описаны базовые ролевые правила коллекции `users` (см. «Роли
пользователей»): они приводятся к реестру на каждом старте
автоматически — на них завязаны права ролей.

## Коллекции и данные

| Коллекция | Назначение | Доступ через API |
|---|---|---|
| `users` | пользователи (почта = открытый ключ + `@seed.local`) | ролевые правила, служебные поля только админ |
| `seed_sessions` | сессии устройств и суперюзера (у маски — поле «от чьего имени») | закрыта; только эндпоинты сервиса |
| `seed_challenges` | челленджи (нонсы), живут 5 минут | закрыта |
| `seed_used` | надгробия использованных нонсов, 24 часа | закрыта |
| `seed_settings` | политики (персональные и глобальные) | закрыта |
| `seed_gateway` | переопределения параметров защиты гейтвея (только отличия от стандарта) | закрыта; только `/api/seed/gateway-config` (суперюзер) |
| `seed_audit` | журнал действий всех действующих лиц (кто, что, от чьего имени) | закрыта; чтение — суперюзер или роль `admin`; запись и удаление запрещены всем |
| `_superusers` | администраторы | только суперюзер |

Поля пользователя, управляемые администратором: `banned` (bool),
`ban_reason` (текст), `banned_until` (дата, пусто = бессрочно),
`role` (выбор `user`/`moderator`/`admin`, см. «Роли пользователей»).
Почта управляется только суперюзером; поля бана и роль — только
администратором; самому себе менять их запрещено (403), а повысить до
`admin` через API нельзя вовсе (только консоль и суперюзер).

Контракт времени:

| Поле | Тип | Заполняется |
|---|---|---|
| `created_at` | автодата | при создании |
| `updated_at` | автодата | при создании и каждом изменении данных |
| `deleted_at` | дата | пусто = запись жива; дата = мягко удалена |

У коллекции `users` системные поля времени стоковые (`created`/`updated`)
— на них завязаны панель и клиентские библиотеки; к ним добавлен
`deleted_at` (метка GDPR-стирания). У сессий обычная активность не
двигает `updated_at` — только реальные изменения данных.

## Консольное управление

Все команды — подкоманды того же бинарника (`./pbseed <группа>
<действие>`), работают без HTTP и токенов: приложение открывается
напрямую, схема доводится реестром. Граница доверия — сам хост: кто
запускает бинарник, тот суперюзер. Каждое действие пишется в журнал
`seed_audit` с актёром `консоль`; разрушительные команды спрашивают
подтверждение (флаг `-y` отключает, `--dry-run` показывает действие
без изменений).

Пользователи (`user`):

| Команда | Действие |
|---|---|
| `user list [--role R] [--banned] [--limit N]` | список: ключ, роль, бан, дата создания |
| `user show КЛЮЧ` | запись целиком: роль, бан-поля, `deleted_at`, число сессий |
| `user role КЛЮЧ РОЛЬ` | назначить роль (создаёт запись заранее) |
| `user ban КЛЮЧ [--reason R] [--until RFC3339]` | бан (пустой срок = бессрочно), действует немедленно |
| `user unban КЛЮЧ` | снять бан, причину и срок |
| `user delete КЛЮЧ [--hard]` | мягкое удаление либо физическое (с чисткой сессий и настроек) |
| `user sessions КЛЮЧ` | живые сессии: устройство, адрес, страна, активность, отзыв |
| `user kill КЛЮЧ (--all\|--grant G)` | отозвать все сессии или одну |
| `user erase КЛЮЧ` | GDPR-стирание (анонимизация + очистка) |

Политики и параметры (`policy`, `settings`, `gateway`):

| Команда | Действие |
|---|---|
| `policy get КЛЮЧ [--user К]` | действующее значение и источник (личная/глобальная/по умолчанию) |
| `policy set КЛЮЧ --value true\|false [--user К] [--lock]` | записать строку; замок только на глобальную |
| `policy delete КЛЮЧ [--user К]` | удалить строку (откат к вышестоящему значению) |
| `settings list [--user К]` | все строки `seed_settings` |
| `gateway list` | параметры гейтвея: значение, источник, стандарт, окружение |
| `gateway set ПАРАМЕТР --value V` | офлайн-оверрайд в базе (значение должно отличаться от стандарта) |
| `gateway reset ПАРАМЕТР` | убрать оверрайд (возврат к окружению/константе) |

Обслуживание (`geo`, `collections`, `db`, `audit`, `firewall`):

| Команда | Действие |
|---|---|
| `geo update [URL]` | обновить геобазу, печатает прогресс до завершения |
| `geo status` / `geo lookup IP` | состояние базы / страна по адресу |
| `collections list` | коллекции с полями и правилами (диагностика дрейфа) |
| `db vacuum` / `db backup ПУТЬ` | сжатие базы / согласованная копия (`VACUUM INTO`) |
| `audit tail [--action A] [--user К] [--limit N]` | последние строки журнала |
| `firewall status` / `unlock-ip [IP]` / `unlock-panel` | состояние фаервола и снятие блокировок |

## Геолокация

Страна берётся из локального файла
[DB-IP IP-to-Country Lite](https://db-ip.com/db/download/ip-to-country-lite)
(ежемесячный выпуск, ~4 МБ скачивание / ~8 МБ на диске, без аккаунта).
Файл лежит рядом с базой: `<pb_data>/geoip/country.mmdb` + `meta.json`.

- Обновление запускает суперюзер (`POST /api/seed/geo/update`);
  одновременно идёт только одна задача; прогресс —
  `GET /api/seed/geo/status`.
- Скачанный файл проверяется целиком (открытие + обход дерева поиска),
  подменяется атомарно; неудачное обновление сохраняет предыдущую базу.
- Приватные/локальные адреса базу не трогают; неизвестная страна — `""`
  (сессии работают и вовсе без базы).
- Атрибуция (лицензия CC BY 4.0): страница, показывающая страну, должна
  ссылаться на DB-IP:

```html
<a href='https://db-ip.com'>IP Geolocation by DB-IP</a>
```
